# CRD upgrade check

Two apps version their CRDs independently of the operator image, in their own
HelmRelease:

- `kubernetes/apps/monitoring/kube-prometheus-stack/app/helmrelease-crds.yaml`
- `kubernetes/apps/database/mariadb-operator/app/helmrelease-crds.yaml`

Renovate opens major-version PRs against those files. Until now the only gate was
the **Flux Local** workflow, which proves the manifests *render*. It does not prove
the apiserver would *admit* them, and it says nothing about whether the CRs already
in Git — or already in the cluster — still validate against the new schemas.

`scripts/crd-upgrade-check.sh` closes that gap, and is explicit about the gap it
cannot close.

---

## Running it

```sh
task crd:check                                        # every helmrelease-crds.yaml
task crd:check path=monitoring/kube-prometheus-stack  # one app
task crd:check:one path=database/mariadb-operator     # same, but fails fast without path

task crd:check:apiserver                              # Tier 3 against a disposable kind cluster
task crd:check:live                                   # + the read-only cluster checks
```

Extra vars accepted by all of them: `base=<git-ref>`, `mode=schema|apiserver`,
`rendered=<file>`, `markdown=<file>`.

The script exits **non-zero only on HIGH findings**. WARN and INFO are for a human
to read.

Targets are discovered with `find kubernetes -name helmrelease-crds.yaml` — a third
CRD chart needs no registration.

### What runs with no cluster and no `age.key`

Everything except the two opt-in live checks. A fresh worktree with neither
`kubeconfig` nor `age.key` runs Tier 1A/1B, Tier 2, and Tier 3 (`--mode=schema` or
`--mode=apiserver`) and reports the live checks as SKIPPED with the reason.

The script never reads `age.key`, never decrypts SOPS, and never writes inside the
repository working tree — all scratch state lives in a `mktemp -d` removed on exit.

## What it checks

### Tier 1 — CRD object safety

Renders the CRDs from the **old** chart (the version on `origin/main`, then `main`)
and the **new** chart (the version in your working tree) and compares them.

| Check | Severity | Why it matters |
|---|---|---|
| 1A CRD present in old, absent in new | HIGH | The app Kustomization has `prune: true`. Flux deletes the CRD, and the apiserver deletes every object of that kind with it. |
| 1B `spec.versions[]` entry removed, or `served` flipped to false | HIGH | Manifests and clients pinned to that version stop resolving. |
| 1B `scope` or `names.kind` changed | HIGH | The apiserver rejects a scope change outright; a kind rename breaks every referencing manifest. |
| 1B storage version moved | WARN | Existing objects stay on the old version until rewritten — a trap for the *next* bump, which may drop it. |
| 1C live `status.storedVersions` contains a version the new chart no longer declares | HIGH | The apiserver refuses the CRD update. This is the failure mode that leaves Flux stuck in a retry loop. |

1C needs `--live` and a reachable cluster. It is read-only (`kubectl get` only, with
an explicit `--request-timeout` on every call) and skips cleanly with a stated reason
when there is no kubeconfig.

If the baseline ref cannot be resolved the script **fails loudly** with the exact
`git rev-parse` commands it tried. It never silently degrades to "no baseline".

### Tier 2 — schema delta

For every CRD version present in both charts, reports four categories, all WARN:

- fields added to `required`
- narrowed enums (values present in the old schema, gone from the new one)
- removed properties
- added or changed `x-kubernetes-validations` (CEL)

Severity is deliberately not inferred beyond those categories — the tool reports,
a human decides.

Every app also gets a `tier2/summary` INFO line:

```
compared 10 CRD version(s); 9 schema(s) differ; 7 optional field(s) added;
0 flagged change(s) (new required / narrowed enum / removed property / CEL)
```

That line exists so "nothing was flagged" is distinguishable from "nothing was
examined". For `prometheus-operator-crds` 29.0.0 → 30.0.1 the honest answer is the
former: nine schemas changed, and every change was a new optional field.

### Tier 3 — CR admission validation

The input is the **fully rendered** cluster manifest, not the raw repo YAML:

```sh
flux-local build all --enable-helm --output-file <tmp>/rendered.yaml kubernetes/flux/cluster
```

That matters: of the 73 `monitoring.coreos.com` CRs in this cluster, only a handful
live in `kubernetes/apps/**` as files. The rest — 26 ServiceMonitors and most of the
40 PrometheusRules — are generated by the kube-prometheus-stack chart and are
invisible to file-level grepping.

Two backends:

| | `--mode=schema` (default) | `--mode=apiserver` |
|---|---|---|
| Mechanism | new CRDs → JSON Schema → `kubeconform` | disposable `kind` cluster, `kubectl apply --dry-run=server` |
| Needs | nothing beyond the pinned toolchain | `kind` + a `docker` CLI (podman only via its docker shim) |
| Runtime, given a rendered manifest | ~3 s | ~40 s (kind creation dominates) |
| Evaluates CEL | **no** | yes |
| Evaluates defaulting | no | yes |
| Flags unknown/removed fields | yes (synthesised `additionalProperties: false`) | yes (kubectl's strict field validation) |

CI uses `--mode=apiserver`. The local default is `--mode=schema` so `task crd:check`
works with only the pinned toolchain. Rendering the cluster manifest adds ~10 s on a
warm cache and dominates a `--mode=schema` run; pass `rendered=<file>` to reuse one.

### Both modes are stricter than Flux — read a HIGH carefully

Neither backend reproduces Flux's apply semantics, and the difference changes what a
HIGH finding *means*.

`apiextensions.k8s.io/v1` structural schemas **prune** unknown fields — the apiserver
drops them and admits the object. It only rejects them when the client asks for strict
field validation. `kubectl` has done so by default since 1.25; **Flux does not**. So:

| Failure class | This check | Flux's actual apply |
|---|---|---|
| Type error, missing required field, CEL violation | HIGH | fails too — a real blocker |
| Unknown or removed field | HIGH | **admitted, field silently pruned** |

For the second row the risk is *lost configuration*, not a failed reconcile: the
setting disappears with no error anywhere. That is arguably the more dangerous
outcome, which is why both modes flag it — but "this will fail to apply" would be the
wrong conclusion. The finding text says which class you are looking at; Tier 2's
`tier2/removed-property` WARN is the same signal caught one layer earlier.

Consequence: `--mode=apiserver` is **not** a superset of `--mode=schema`. It adds CEL
and defaulting; it does not subsume anything.

`--live` additionally pulls the CRs that exist in the cluster, strips
`status`/`managedFields`/`creationTimestamp`/`resourceVersion`/`uid`/`generation`/
`ownerReferences`, and validates those too. That is the only way to catch a CR that
exists in the cluster but not in Git.

## What it does NOT cover

Every run ends with this list. It is not boilerplate — each item is a real way the
check can be green and the upgrade can still break.

1. **Validating admission webhooks.** kube-prometheus-stack ships a
   prometheus-operator admission webhook that PromQL-parses `PrometheusRule`
   expressions and rejects invalid ones. Neither backend models it. A rule with a
   syntactically broken `expr` passes both tiers and is rejected by the live cluster.
2. **CEL rules and server-side defaulting**, in `--mode=schema`. JSON Schema cannot
   evaluate `x-kubernetes-validations`. If Tier 2 flags a CEL change, re-run with
   `--mode=apiserver` before merging.
3. **CRs that exist only in the live cluster** — created by an operator, applied by
   hand, or orphaned by a removed app — unless `--live` was used. CI never uses it:
   there is no kubeconfig in CI, by design.
4. **Operator/CRD version compatibility.** The operator image is pinned by a separate
   HelmRelease and bumped by a separate Renovate PR. A CRD chart can be perfectly
   schema-valid and still be ahead of (or behind) the running operator. Nothing here
   correlates the two.
5. **Upgrade mechanics**: conversion webhooks, storage migration of existing objects,
   and Helm/Flux field-ownership conflicts.

Also worth knowing:

- `spec.valuesFrom` is not resolved. If a CRD HelmRelease ever gates CRDs on a
  ConfigMap/Secret value, the rendered CRD set here will not match reality. The run
  notes this when it sees `valuesFrom`.
- `--mode=schema` reports unknown and removed fields because the converter
  synthesises `additionalProperties: false`; pass `--lax-schema` to turn that off if
  it ever produces a false positive.

  **How far that has actually been exercised:** all 73 rendered CRs of
  `prometheus-operator-crds` validate clean. That is one chart. `mariadb-operator-crds`
  has never been through this path — the rendered manifest contains no CRs for its
  group, so it reports `tier3/no-crs` and the converter is never invoked on it. The
  synthesis is only safe when a CRD's root schema declares `apiVersion`/`kind`/
  `metadata`; `controller-gen` emits all three, but a hand-written CRD that omits them
  would fail *every* CR at the root. Treat the first HIGH from a chart other than
  `prometheus-operator-crds` as suspect, and check it against `--lax-schema` before
  believing it.

## CI

Workflow: `.github/workflows/crd-upgrade-check.yaml`.

- Triggers on PRs touching `**/helmrelease-crds.yaml` (plus `workflow_dispatch`) via
  the workflow's own `paths:` filter. There is deliberately no `changed-files`
  pre-job: Flux Local needs one because it has no `paths:` filter and must decide
  per-run, but here that would just re-derive a decision GitHub already made, at the
  cost of a runner.
- `permissions: contents: read` at workflow level. The check job keeps that; only the
  separate `comment` job gets `pull-requests: write`.
- No kubeconfig and no SOPS age key are available to the job. The only cluster it
  talks to is the ephemeral `kind` cluster created by the SHA-pinned
  `helm/kind-action`.
- **Every version string here is Renovate-trackable.** `flux-local` runs through the
  `uses: docker://…` form rather than `docker run` inside a `run:` block, because only
  the former is visible to Renovate's `github-actions` manager — otherwise Renovate
  would bump the identical pin in `flux-local.yaml` and silently leave this one
  behind. The kind node image is not pinned at all: `helm/kind-action` ships a default
  matched to its own release, so bumping the action SHA carries it. In
  `scripts/crd-upgrade-check.sh` the same two images are annotated with
  `# renovate: datasource=docker depName=…` and kept as bare `KEY=value` version
  lines, which is the shape `.renovaterc.json5`'s custom manager matches — a quoted
  `"image:tag"` would capture the quotes into the version.
- **Report-only.** The script step is `continue-on-error: true`; the report goes to
  `$GITHUB_STEP_SUMMARY` and to a sticky PR comment. A HIGH finding does not fail the
  build.

### Promotion criterion

Flip the check to blocking — drop `continue-on-error: true` from the
`Run crd-upgrade-check` step — once **five consecutive CRD-chart Renovate PRs have
run it with zero false-positive HIGH findings**. At the current cadence (a
`prometheus-operator-crds` or `mariadb-operator-crds` bump every few weeks) that is
roughly one quarter of real traffic. A false positive means a HIGH finding on a PR
that turned out to be safe to merge as-is.

Until then, treat a HIGH finding as "read this before merging", not "blocked".

## Tooling notes (verified, not assumed)

These were checked against the actual tools; several contradict the obvious
assumption.

- **`kubeconform -strict` does not synthesise `additionalProperties: false`.** It
  only expands `{{.StrictSuffix}}` in the schema location and rejects duplicate YAML
  keys. Unknown fields are invisible unless the schema itself closes the object —
  which CRD structural schemas do not. The converter in this script adds
  `additionalProperties: false` itself, skipping any node with
  `x-kubernetes-preserve-unknown-fields: true` and any node carrying
  `anyOf`/`oneOf`/`allOf`/`not` (a junctor branch may legitimately list a subset of
  properties).
- **`-schema-location` exposes `.Group`.** The full template struct is
  `{NormalizedKubernetesVersion, StrictSuffix, ResourceKind, ResourceAPIVersion,
  Group, KindSuffix}`. `.ResourceKind` is lowercased, `.ResourceAPIVersion` is the
  version alone (`v1beta1`, not `group/v1beta1`). Schemas are therefore written to
  `<group>/<kind>_<version>.json`, which keeps same-kind-different-group and
  multi-version CRDs from colliding.
- **`x-kubernetes-int-or-string` needs no conversion.** In these charts those nodes
  carry no `type` (sometimes an `anyOf` of integer/string plus a `pattern`), which is
  already permissive in JSON Schema. Neither chart uses `nullable` or
  `exclusiveMinimum`, the two OpenAPI-3.0-isms that would need rewriting.
- **`kubectl apply` (client-side) cannot apply these CRDs at all.** The `prometheuses`
  CRD alone is ~834 KB, and the `last-applied-configuration` annotation it writes
  exceeds the apiserver's 262144-byte limit:
  `metadata.annotations: Too long: may not be more than 262144 bytes`. Flux applies
  CRDs with `CreateReplace`, which never writes that annotation, so the script mirrors
  Flux — `kubectl create`, falling back to `replace` — rather than kubectl's default.
  Rendered CRs are dry-run with `--server-side` for the same reason.
- **`flux-local build all` writes into the tree it is pointed at** (it shells out to
  `flux build ks`, which generates a `kustomization.yaml`), and it calls
  `git rev-parse --show-toplevel`, which fails in a linked worktree whose `.git` is a
  file. The script therefore renders a throwaway copy of `kubernetes/` in its temp
  dir, `git init`s it, and points flux-local at that. The repo working tree is never
  touched. It also hardcodes a 60-second per-`helm template` timeout with a
  concurrency of 20, so a cold run on a small container runtime can time out; the
  script retries once and degrades Tier 3 to SKIP rather than failing.
- `--skip-crds` and `--skip-secrets` are confirmed to be `flux-local build all`'s
  defaults, so no age key is ever needed for the render.

## Tool pinning

Everything the default path needs is already pinned in `.mise.toml`: `helm`, `yq`,
`jq`, `kubectl`, `kubeconform`, `git`. Nothing was added.

Two tools are resolved at run time instead:

- **flux-local** ships as a container image, not a binary; the script uses a native
  `flux-local` if one is on `PATH`, else `docker run ghcr.io/allenporter/flux-local:v8.0.1`
  (the same image and tag the Security Scan workflow uses).
- **kind** is only needed for `--mode=apiserver`, which is not the local default. CI
  gets it from the pinned `helm/kind-action`. Locally, install it yourself or stay on
  `--mode=schema`; the script says so rather than failing obscurely.
